# SPEC.md — 원장의 스키마와 검사 목록

이 파일은 `docs/decisions/` 원장의 **스키마와 검사 목록의 정본**이다. 판단을 요구하는 조항은
세션 지시 §3.7(R-6 ~ R-10)과 §5.6이 들고, 이 파일은 그것을 기계가 읽는 형태로 내린다.

**검사 목록이 먼저이고 스키마는 거기서 유도됐다.** 반대 순서로 가면 조항은 있는데 검사가 없는
자리가 생긴다. 그래서 이 문서는 §2에 검사를 먼저 놓고 §3에 스키마를 놓는다. 스키마의 모든
필드는 §2의 어느 검사가 읽는 것이며, 어느 검사도 읽지 않는 필드는 두지 않는다.

---

## 0. 정체와 비목적

### 0.1 원장이 드는 것

낙착과 그 **사유와 실측 근거**다. 규율의 집행 문면은 세션 지시와 `CLAUDE.md` 가 들고 원장은
그것이 어떤 실패를 잡으려 섰는지를 든다. 둘이 드는 것이 다르므로 전사가 아니다.

### 0.2 원장이 들지 않는 것

- **코드의 위치.** 파일 경로와 줄번호를 항목에 넣지 않는다. 코드 쪽 링크는 Lean 주석의
  `-- DD:<id>` 가 들고 `grep` 으로 복원한다. 경로를 넣으면 리팩터링마다 원장이 낡는다
- **값.** 공리 기준선과 툴체인 핀과 오염 어간은 `docs/baseline.md` 가 든다
- **아크와 페이즈의 값.** `arcs.json` 이 든다. 원장은 그것을 `origin` 으로 지목만 한다
- **살아 있음.** 저장하지 않고 유도한다. 자기를 가리키는 폐기 레코드가 없으면 살아 있다

### 0.3 수정하지 않는다

항목이 일단 쓰이면 어떤 필드도 고치지 않는다. 폐기는 **폐기 레코드를 새로 쓰는 것**이며 원
항목을 건드리지 않는다. 상태 필드를 고치는 방식은 추가로 위장한 수정이므로 쓰지 않는다(R-9).

**재분류도 수정이 아니다.** 구멍이 해소되면 결정 항목을 새로 쓰고 그 구멍을 가리키는 폐기
레코드를 쓴다. 구멍 항목은 제자리에 그대로 남는다. 그래서 항목이 파일 사이를 옮겨 다닐 일이
없다.

## 1. 파일 구성

| 파일 | 담는 것 |
|---|---|
| `decisions.json` | 결정. 규율 조항과 확정 결정과 독해 산출 |
| `deferred.json` | 정의 구멍과 탐구 미결 |
| `rejected.json` | 기각한 정의 후보 |
| `retirements.json` | 폐기 레코드 |
| `docs/arcs.json` | 아크와 페이즈와 패치 |

**컨테이너는 최상위 키 둘이다.** `spec` 이 이 문서를 가리키고, 레지스터 이름을 키로 한 배열이
entry 를 든다.

```json
{ "spec": "docs/decisions/SPEC.md", "decisions": [ … ] }
```

`docs/arcs.json` 이 이미 그 관례로 서 있어 따랐다. **산문 필드를 두지 않는다.** `arcs.json` 의
`note` 에 해당하는 자리가 없으며, 원장이 드는 것은 entry 뿐이다.

이 모양은 첫 병합에서 집행이 물어 정해졌다. 카드가 entry 만 들고 지시서가 「파일을 세우고 entry
를 적는다」까지를 들어 감싸는 구조가 어느 쪽 문면에도 없었다. **§6.4 (7)이 요구한 재료가 비어
있었고 집행이 그것을 지어내는 대신 알렸다.**

**ID 공간은 네 파일에 걸쳐 하나다.** `CF-<n>` 단조 증가이며 재사용하지 않는다. 종류는 파일이
들고 접두사에 박지 않는다. 참조 구현에서 종류를 접두사에 박은 결과 같은 계열이 두 파일에 걸치게
됐고, 그것을 잡으려고 검사를 하나 더 세워야 했다.

**`invariants` 파일을 따로 두지 않는다.** 불변식은 종류가 아니라 **티어**이며 `decisions.json`
안에서 `tier` 가 든다. 참조 구현은 둘을 다 두어 같은 축이 두 자리에 섰다.

**`glossary` 파일도 두지 않는다.** V-1이 **용어집은 Lean 파일**이며 개념의 존재와 관계만 담는
것으로 이미 정했으므로, 같은 내용을 JSON으로 또 두면 §0.2가 금지한 전사가 된다. 정본은
`CrisisFramework/Glossary/Core.lean` 이다. 셋이 다른 것을 들어 빠지는 것이 없다.

| 무엇 | 거처 |
|---|---|
| 개념의 존재와 관계 | Lean 용어집 파일 (V-1·V-2) |
| **왜 이렇게 분할했는가** | `decisions.json` |
| 기각한 분할 후보와 사유 | `rejected.json` |

D-7의 탐지(정의 파일의 개념이 용어집에 있는가)도 Lean grep이라 JSON을 요구하지 않는다. 참조
구현에서 용어집이 JSON이었던 것은 그쪽에 Lean 용어집이 없었기 때문이며, 스키마를 옮기면서
그 차이를 놓쳤다.

## 2. 검사 목록

검사는 스물넷이다. 실패시키는 것 열여덟, 보고만 하는 것 넷, 아크 종료 시에만 도는 것 둘이다.
**번호는 불변 앵커이므로 재배치하지 않는다.** 뒤에 선 검사가 앞 번호 사이에 끼어 보이는 것은
그 때문이다.

각 검사는 **그것이 잡아야 할 위반을 주입했을 때 실패하는지**를 확인한다(§3.10-1 음성 대조).
통과만 보고 검사가 동작한다고 판단하지 않는다. 주입 시험의 대상을 검사마다 함께 적는다.

### 2.1 실패시키는 검사 (열여덟)

| | 검사 | 잡는 실패 | 주입 시험 |
|---|---|---|---|
| **1** | `id` 가 `CF-<n>` 형식이고 전 파일에서 유일한가 | 마커 충돌 | 같은 id를 두 파일에 넣는다 |
| **2** | `origin.arc` 가 `arcs.json` 의 아크 이름에 실재하는가 | **아크명 누락** | 없는 아크명을 적는다 |
| **3** | `origin.phase` 가 그 아크의 `phases` 에 있는가 | 페이즈가 선언 없이 생기는 것 | 선언되지 않은 페이즈를 적는다 |
| **3-a** | `origin.phase` 가 `origin.arc + "-" + <n>` 형태인가 | 아크와 페이즈가 어긋나는 것 | 다른 아크의 페이즈명을 적는다 |
| **4** | 3이 실패할 때 `arcs.json` 의 `patches` 가 그 페이즈에 권한을 주는가 | 계획이 조용히 달라지는 것 | 패치 없이 페이즈를 늘린다 |
| **4-a** | `op: move`·`split` 인 패치의 `from` 이 그 아크의 `phases` 에 있는가 | 있지도 않은 페이즈에서 옮겼다고 적는 것 | 없는 페이즈를 `from` 에 적는다 |
| **5** | `status: closed` 인 아크에 새 항목이 드는가 | 아크 종료의 무의미화 | 닫힌 아크로 항목을 쓴다 |
| **6** | `tier` 가 `invariant`·`policy`·`finding` 중 하나인가 | 티어 어휘 드리프트 | `tactical` 을 적는다 |
| **7** | `tier: invariant` 인 항목의 `check` 가 `verify.sh` 의 선언된 단계에 실재하는가 | **티어의 거짓 주장** | 없는 단계명을 적는다 |
| **8** | 폐기 레코드의 `target` 이 실재하고 한 대상에 폐기가 둘 이상이 아닌가 | 폐기 정합 | 같은 대상을 두 번 폐기한다 |
| **9** | 폐기 레코드에 `original` 과 `reason` 이 비어 있지 않은가 | 폐기 사유의 소실 | `reason` 을 비운다 |
| **10** | **폐기된 id를 살아 있는 것처럼 참조하는 자리가 있는가** | 유령 | 폐기된 id를 `related` 에 넣는다 |
| **11** | `deferred` 항목에 `reopen_when` 이 있고 `kind` 가 넷 중 하나인가 | 트리거 없는 등재 | `kind` 를 비운다 |
| **12** | `reopen_when.ref` 가 `kind` 별 **형식**을 만족하는가 | 트리거가 해소될 수 없는 형인 것 | 아크가 아닌 문자열을 `arc_phase` 에 적는다 |
| **13** | Lean의 `DD:` 표지가 실재하고 폐기되지 않은 id를 가리키는가 | 끊긴 표지 | 없는 id를 주석에 적는다 |
| **14** | `DD:` 항목의 `layer` 가 그 파일이 사는 층과 같은가 | 결정이 엉뚱한 층에서 인용되는 것 | 회계층 파일에서 정의층 항목을 지목한다 |
| **15** | `names` 의 규율 ID가 원장 전체에서 유일한가 | 한 규율이 두 항목에 붙는 것 | 같은 규율 ID를 두 항목에 적는다 |
| **23** | `statement`·`basis` 에 나타난 규율 ID 토큰이 어느 항목의 `names` 에 실재하고 폐기되지 않았는가 | **규율 지목의 유령** | 폐기된 규율 ID를 근거로 적는다 |

**검사 10의 범위는 원장 밖으로 나간다.** 폐기된 id를 참조하는 자리가 셋이다. 원장 안의
`related` 와 `reopen_when.ref`, Lean 파일의 `DD:` 표지, `docs/` 산문의 인용이다. 셋을 다 훑되
**폐기 레코드 자신의 `target` 과 `original` 은 제외한다.** 그것은 폐기를 기록하는 자리이지 산
참조가 아니다.

**검사 23이 규율 지목의 유령을 잡는다.** 원안은 이 일을 검사 15에 맡겼는데, 각 항목의 `names`
가 **자기 규율 ID**를 들므로 자기가 자기를 보는 꼴이 되어 아무것도 잡지 못했다. 규율이 다른
규율을 지목하는 자리는 `names` 가 아니라 `statement` 와 `basis` 의 산문이다.

**이 결함류는 이 프로젝트에서 두 번 났다.** `project-setup-v0` 이 폐기된 A-4를 Mathlib 핀 정책의
근거로 들고 있었고, `CLAUDE.md` 가 폐기된 W-2와 R-1을 출처 주석으로 지목하고 있었다. 둘 다 사람이
전수 대조해서 잡았다.

**검사 23은 자기 폐포로 성립한다.** 규율의 정본인 세션 지시는 리포 밖에 있어 대조할 수 없다.
그런데 규율 조항이 원장 항목으로 들어오므로, 산문의 규율 ID 토큰이 어느 항목의 `names` 에
실재하는지를 물으면 리포 안에서 닫힌다. **규율을 먼저 역유입해야 이 검사가 의미를 갖는다**(J-23).

토큰의 형은 `<계열>-<수>` 이며 계열은 P·A·C·L·D·T·R·N·V·W·Q·B·O·G·S·F·J·K·PH-R이다. 원장
ID(`CF-<n>`)와 폐기 레지스터 지목(`§3.12-7`)은 대상이 아니다.

**`E` 를 계열에서 뺀다.** 규율의 E는 추출 템플릿 하나뿐이고 번호를 갖지 않는 반면 `E-nn` 은
추출 기록의 번호이며 별개 네임스페이스다. 넣어 두면 `basis` 가 추출 기록을 인용할 때마다
유령으로 잡힌다. 실측하면 첫 적재에서 141건이 그 형이었다. `E-nn` 의 해소는 검사 12의
`extraction` 쪽이 본다.

**폐기된 규율을 지목하는 것 자체는 정당하다.** A-6의 `basis` 가 A-4를 대체 대상으로 드는 것이
그 예다. 그것과 「폐기된 것을 산 것처럼 드는 것」을 기계가 가르려면 구조가 필요하므로, **폐기된
규율 ID를 산문에서 지목하려면 `related` 에 그 항목의 원장 ID를 넣는다.** 넣지 않은 지목은
실패시킨다. 지목이 의도된 것임이 그 자리에 드러난다.

폐기 레코드 자신의 `original` 과 `reason` 은 이 검사의 유니버스 밖이다. 폐기를 기록하는 자리이지
산 지목이 아니며, 검사 10이 같은 예외를 이미 둔다.

### 2.2 보고만 하는 검사 (넷)

실패시키지 않고 계수와 목록을 낸다.

| | 보고 | 왜 실패가 아닌가 |
|---|---|---|
| **16** | `reopen_when` 이 충족된 이연 항목 | **발화 탐지.** 트리거를 써 놓고 아무도 안 보면 구멍이 영영 잔다 |
| **17** | `reopen_when: null` 인 항의 계수 | R-7이 등재는 허용하되 계수로 보고하게 했다 |
| **18** | 아크별 `blocking` 구멍의 처분 내역 | 아크를 닫을 때 셋 중 하나여야 하나, 내역 자체는 보고 대상 |
| **19** | `CF-<n>` 번호의 결번 | 결번이 곧 결함은 아니나 삭제의 흔적일 수 있다 |

**검사 16이 없으면 `blocking` 트리거가 무의미하다.** 발화 신호가 리포에 흔적을 남긴다는 것이
R-7의 전제인데, 그 흔적을 읽는 쪽이 없으면 흔적만 남고 아무 일도 일어나지 않는다.

### 2.3 아크 종료 시 검사

아크를 닫을 때만 도는 검사다. `status` 를 `closed` 로 바꾸는 커밋에서 실행한다.

| | 검사 |
|---|---|
| **20** | 그 아크에 걸린 구멍마다 해소됐거나 이관됐는가 |
| **21** | 그 아크에 걸린 `blocking` 구멍마다 발화했거나, 진술이 쓰였는데 막히지 않아 해소됐거나, 진술을 쓰지 않아 이월됐는가 |

21이 없으면 **발화시킬 진술을 아무도 쓰지 않은 구멍이 영영 자고, 겉으로는 해소된 것과 구별되지
않는다.**

## 3. 스키마

필드마다 그것을 읽는 검사 번호를 단다. **어느 검사도 읽지 않는 필드는 두지 않는다.**

### 3.1 공통 필드

모든 레지스터의 항목이 갖는다.

| 필드 | 형 | 검사 | 뜻 |
|---|---|---|---|
| `id` | `"CF-<n>"` | 1 | 불변 앵커 |
| `origin` | 객체 | 2·3·3-a·4·5 | **이 항목이 원장에 쓰인 페이즈** |
| `statement` | 문자열 | | 무엇이 정해졌는가. 한 문장 |
| `basis` | 문자열 | | **언제 무엇이 이것을 낳았나.** 경위와 실측의 지목 |
| `related` | `["CF-<n>"]` | 10 | 다른 항목 참조 |

`origin` 의 내부는 이렇다.

```json
"origin": {
  "arc":   "claim",
  "phase": "claim-3",
  "kind":  "decision_session",
  "date":  "2026-09-19"
}
```

**`arc` 와 `phase` 의 중복은 의도된 것이다.** 값 하나만 옮겨 적어도 아크가 따라오고, 둘이
어긋나면 검사 3-a가 잡는다. 참조 구현이 페이즈를 그리스 문자 하나로 두어 산문에 무심코
흩뿌려졌고 그때마다 아크명이 빠졌다. 실측하면 2088건이었다.

`kind` 는 `decision_session` · `reading` · `handoff_return` 셋이다.

**`origin` 은 그 항목을 쓴 결정 세션의 페이즈다.** 결정이 난 페이즈도 아니고 병합이 일어난
페이즈도 아니다. 셋이 갈리는 자리가 실제로 있다. 규율 조항은 아크 개념 이전에 결정됐고,
`charter-6` 이 그것을 항목으로 썼으며, 병합은 `charter-7` 이 한다.

`origin: charter-6` 은 「charter-6 에서 이 항목을 썼다」는 참인 진술이며, 내용이 그전에 섰다는
사실은 `basis` 가 산문으로 든다. **병합 페이즈는 기록하지 않는다.** 그것은 커밋이 든다.

**`source` 필드를 두지 않는다.** 원장 항목이 리포의 다른 문서를 지목하면 **그 문서가 사라질 때
원장이 깨지고, 원장은 수정 불가이므로 고칠 수단이 폐기 레코드뿐이다.** 참조 구현의 세션 지시가
같은 것을 적어 두었다. 원장의 해소 검사가 파일시스템을 읽으므로 추적되지 않는 파일에 의존하는
해소는 새 클론에서 깨진다.

**지목보다 수록이 낫다.** C-4의 원문이 `verification-01` 한 곳에만 있었는데, 그 문서를 `source`
로 가리키는 대신 폐기 레코드의 `original` 에 문면을 담으면 문서가 사라져도 원문이 원장에 영구히
남는다. **원장은 자기완결이어야 하며 어떤 외부 문서의 수명에도 매달리지 않는다.**

**`statement` 와 `basis` 는 조항 문면의 전사가 아니다.** 규율 조항의 논증은 세션 지시가 들고
원장은 그 조항이 어느 실측에서 어떻게 나왔는지를 든다. 둘이 드는 것이 다르므로 §0.2의 전사
금지에 걸리지 않는다.

| | 드는 것 |
|---|---|
| 세션 지시 | **왜 이 규칙인가.** 논증 |
| 원장 `basis` | **언제 무엇이 이것을 낳았나.** 경위와 실측의 지목 |

C-9를 예로 들면 이렇다.

```
statement : 정의층·회계층·관측층에서 전면 simp 호출을 금지한다
basis     : 3차 세션 ℤ 이행 검증에서 mul_eq_zero 가 요구하는 NoZeroDivisors ℤ
            인스턴스를 통해 기준선이 오염된 것이 실측됐다. 음성 대조 NC-5 가
            그 검사가 실제로 잡는다는 것을 확인했다. ph2-01 §5 에서 개정
            후보로 제안되어 charter-1 에서 승인됐다.
names     : ["C-9"]
```

전면 `simp` 를 쓰면 공리 의존이 소스에서 읽히지 않는다는 **논증**은 세션 지시에만 있다. 원장은
그것이 어느 실측에서 나왔는지를 든다.

`statement` 도 조항 문면을 그대로 옮기지 않는다. 원장을 읽는 사람이 이 항목이 무엇인지 알아보게
하는 한 문장이며, 정본은 `names` 가 지목한다.

**입도는 조항 하나가 항목 하나다.** `basis` 가 경위로 좁혀지므로 항목이 비대해지지 않는다. A-6의
다섯 항은 조항의 내용이고 세션 지시가 들며, 원장은 A-6이 A-4를 대체해 선 계기만 든다.

### 3.2 `decisions.json`

| 필드 | 형 | 검사 | 뜻 |
|---|---|---|---|
| `tier` | `invariant`\|`policy`\|`finding` | 6·7 | R-10 |
| `layer` | 아래 여섯 | 14 | 어느 형식층의 결정인가 |
| `names` | `["C-10", ...]` | 15·23 | 이 항목이 드는 규율 조항의 이름 |
| `check` | 문자열 | 7 | `verify.sh` 의 단계 id. `tier: invariant` 면 필수 |

`layer` 의 값은 `glossary` · `definition` · `accounting` · `dynamics` · `observation` · `meta`
여섯이다. 앞의 다섯이 형식층이고 `meta` 는 층에 갇히지 않는 것이다.

**`meta` 는 「Lean에서 지목되지 않는다」가 아니다.** A-3은 층을 가리지 않고 모든 `structure` 에
걸리므로 `Glossary/` 와 `Definition/` 양쪽에서 `DD:` 로 지목되는데, `layer` 가 하나뿐이라 어느
값을 넣어도 검사 14가 한쪽을 실패시킨다. 그래서 **검사 14는 `meta` 를 건너뛴다.**

검사 14가 실제로 잡는 것은 **층에 매인 결정이 다른 층에서 인용되는 경우**다. L-4와 L-15는
`accounting` 이고 L-13은 `definition` 이며 L-14는 `observation` 이고 V-1·V-2는 `glossary` 다.
동학층 파일이 L-15를 지목하면 그것이 오류다.

**검사 14의 대응표.**

| `layer` | 디렉터리 |
|---|---|
| `glossary` | `CrisisFramework/Glossary/` |
| `definition` | `CrisisFramework/Definition/` |
| `accounting` | `CrisisFramework/Accounting/` |
| `dynamics` | `CrisisFramework/Dynamics/` |
| `observation` | `CrisisFramework/Observation/` |
| `meta` | **층에 갇히지 않는다.** 검사 14가 건너뛴다 |

`names` 는 선택이다. 규율 조항이 아닌 결정은 이름을 갖지 않는다.

### 3.3 `deferred.json`

| 필드 | 형 | 검사 | 뜻 |
|---|---|---|---|
| `layer` | 위 여섯 | 14 | |
| `reopen_when` | 객체 \| `null` | 11·12·16·17 | 재개 트리거 |

```json
"reopen_when": { "kind": "blocking", "ref": "claim", "what": "발동조건 문법이 V-2의 네 관계로 표현되지 않는 자리" }
```

**`kind` 는 넷이다.**

| `kind` | `ref` | 검사 12가 보는 것 | 실재를 보는 곳 |
|---|---|---|---|
| `artifact` | 리포 경로 | 경로의 형식 | 검사 16 |
| `extraction` | `E-nn` | `docs/reading-queue-v0.md` 의 번호 | 검사 16 |
| `arc_phase` | 아크 이름 | `arcs.json` 에 실재 | 같음 |
| `blocking` | 그 진술을 쓸 아크 이름 | `arcs.json` 에 실재 | 같음 |

**검사 12가 `artifact` 의 실재를 보지 않는다.** 그 파일이 서는 것이 곧 재개 조건이므로, 실재를
요구하면 **발화 조건이 이미 충족된 트리거만 등재할 수 있게 되어** 검사 16과 정반대로 선다.
실측하면 첫 적재의 `artifact` 열아홉 가운데 열셋이 아직 없는 파일을 가리켰고 그것이 정상이다.

`arc_phase` 와 `blocking` 은 다르다. 아크는 `arcs.json` 이 `reserved` 로 미리 세울 수 있으므로
실재를 요구해도 등재가 막히지 않는다.

`blocking` 은 "이것 없이 진행되는 동안은 자고, 이것을 요구하는 진술이 실제로 막히면 깬다"를
뜻한다. 발화 신호는 그 자리의 `sorry` 이거나 빌드 실패이거나 막힘 보고이며 셋 다 리포에 흔적을
남긴다. **판정자가 사람이 아니라 형식화라는 점에서 P-1과 같은 축이다.**

`arc_phase` 의 `ref` 가 아직 열리지 않은 아크를 가리킬 수 있다. `arcs.json` 에 `status:
reserved` 로 이름만 예약해 두면 된다. 범위 밖으로 밀려 있는 구멍이 거기에 걸리고, 예약 아크가
열리는 순간 한꺼번에 발화한다.

`reopen_when: null` 은 허용하되 검사 17이 계수로 보고한다. **재개 조건을 못 쓴다는 사실 자체가
P-1이 찾는 종류의 관측일 수 있다.**

### 3.5 `retirements.json`

| 필드 | 형 | 검사 | 뜻 |
|---|---|---|---|
| `target` | `"CF-<n>"` | 8·10 | 폐기되는 항목 |
| `original` | 문자열 | 9 | 그 항목의 원문 |
| `reason` | 문자열 | 9 | **어떤 실패를 잡으려 섰고 왜 그 틀이 깨졌는가** |
| `replaced_by` | `"CF-<n>"` \| `null` | 8 | 대체 |

폐기 레코드 자신도 `id` 와 `origin` 을 갖는다. 언제 어느 페이즈에서 폐기했는지가 남아야 하기
때문이다.

**`reason` 이 비면 안 되는 근거는 실측이다.** 참조 구현은 폐기 사유를 패치 문서에 두어 원장만
보고는 그 조항이 어떤 실패를 잡으려 섰는지 알 수 없었다. 그리고 원 초안이 소실된 계열은 문면을
패치 헤더에서 재구성해야 했다.

**소급분의 `original` 예외.** 첫 적재의 폐기 레코드 스물하나 가운데 여덟은 원문이 어디에도 없다.
규율 v1~v3 시절의 한 줄형 레코드가 사유와 대체만 담았고 그 판의 문서가 이 프로젝트에 없기
때문이다. 그런 항은 `original` 에 **「원문이 기록되지 않았다」와 현존하는 서술의 자리**를 적는다.
지어내면 §5.7이 금지한 형이 된다.

**이 예외는 첫 적재(`charter-6`)의 폐기 레코드에만 걸린다.** 그 뒤에 서는 폐기는 원문을 담아야
하며, 그러지 않으면 이 문면이 검사 9를 우회하는 경로가 된다.

복원 가능성을 실측하면 갈린다. C-4는 `verification-01` §3-4가 블록인용으로 원문을 들고 있어
옮겨 쓸 수 있고, A-4는 같은 문서가 서술만 하므로 원문이 아니며, D-6과 L-1·L-2·L-3·L-6·L-7은
지목만 남아 있다.

### 3.6 `arcs.json`

```json
{
  "arcs": [
    {
      "name": "claim",
      "discriminator": "청구권 발동조건을 어떤 문법으로 쓰는가",
      "ph": "PH-2",
      "phases": ["claim-1", "claim-2", "claim-3"],
      "status": "open",
      "opened": "2026-09-19",
      "closed": null,
      "holes": ["CF-120", "CF-121"],
      "cq": ["CQ-fin-1"]
    }
  ],
  "patches": [
    {
      "arc": "claim",
      "op": "move",
      "from": "claim-3",
      "phase": "claim-4",
      "what": "무엇이 옮겨졌는가",
      "why": "...",
      "origin": { "arc": "claim", "phase": "claim-3", "kind": "decision_session", "date": "..." }
    }
  ]
}
```

| 필드 | 검사 | 뜻 |
|---|---|---|
| `name` | 2 | 아크 이름. `origin.arc` 가 이것을 가리킨다 |
| `discriminator` | | **판별선 하나.** 둘 이상이면 아크가 아니다 |
| `phases` | 3·3-a | **개막 시 정한 전량** |
| `status` | 5 | `open` · `closed` · `reserved` |
| `holes` | 20·21 | 이 아크에 걸린 구멍 |
| `cq` | | 내리려는 `CQ-fin` 항 |

`patches` 의 `op` 는 `add` · `move` · `split` · `drop` 이다. **추가만 하며 앞 레코드를 고치지
않는다.** 이 배열이 검사 4의 권한 원천이므로, 선언되지 않은 페이즈로 항목이 들어오면 여기에
레코드가 있어야 통과한다. **관행이던 것이 기계 검사가 된다.**

**`op` 의 대상은 페이즈만이 아니라 작업 내용이기도 하다.** 페이즈 목록 자체를 늘리는 것이
`add` 이고, 이미 선언된 페이즈 사이에서 작업이 옮겨 가는 것이 `move` 다. 뒤가 이 프로젝트에서
더 흔하다. 구멍이 열려 계획이 바뀌는 것이 상시이기 때문이다.

| 필드 | 검사 | 뜻 |
|---|---|---|
| `op` | | `add` · `move` · `split` · `drop` |
| `from` | 4-a | `move`·`split` 의 출발 페이즈 |
| `phase` | 4 | 도착 페이즈. `add` 면 새로 선언되는 페이즈 |
| `what` | | 무엇이 옮겨졌는가. 페이즈 조작이면 비운다 |
| `why` | | 무엇이 계획을 바꾸었는가. **이것이 P-1 산출의 증거다** |

`what` 과 `why` 를 읽는 검사가 없다. 기계가 판정할 수 없는 문면이며 W-6의 리뷰 항목이다. 다만
`why` 는 이 배열을 두는 이유 자체이므로 비우지 않는다.

`discriminator` 를 읽는 검사가 없다. 판별선이 하나인지는 기계가 셀 수 없으므로 W-6의 리뷰
항목이다. 필드로 두는 것은 아크를 열 때 그것을 쓰게 강제하기 위해서다.

**`holes` 는 그 아크가 낳은 구멍이 아니라 그 아크가 해소해야 할 구멍이다.** 둘을 가르지 않으면
아크를 닫을 때 검사 20이 그 아크가 낳았을 뿐 다른 아크가 해소할 구멍까지 요구한다. `primary` 가
낳은 예순다섯은 어느 아크에도 아직 배정되지 않았으므로 어느 `holes` 에도 들지 않는다.

**`scope_doc` 을 두지 않는다.** 아크의 논증은 원장의 결정 항목이 들고 값은 이 파일이 든다.
아크마다 개막 문서를 따로 두면 같은 것이 세 자리에 살게 된다. 원장이 낙착을 들고 이 파일이
값을 들며 개막 문서가 그 둘을 산문으로 다시 드는 형이다. **원장 항목이 외부 문서를 지목하지
않는다는 것(J-29)과 같은 축이다.**

`patches` 의 `why` 도 요지만 든다. 계획을 바꾼 논증은 원장의 결정 항목이 들고, 그 항목과
`statement`·`basis` 의 분업이 여기서도 그대로 걸린다.

## 4. 검증기

`scripts/check_wiki.py` 가 §2의 검사를 돈다. `scripts/verify.sh` 가 그것을 호출하고 CI가
`verify.sh` 를 돈다.

**Claude Code는 이 검증기와 CI 워크플로를 고쳐 통과시키지 않는다.** 검사가 실패하면 그 실패가
산출물이다.

**현행 뷰를 매 커밋에 생성한다.** 살아 있음을 저장하지 않고 유도하므로(§0.2) 항목 하나만 봐서는
그것이 살아 있는지 알 수 없다. 폐기 색인을 함께 읽어야 하는 비용을 생성물이 흡수한다. 생성물은
원장이 아니므로 고쳐도 되고 지워도 되며, 매번 다시 만들어진다.

## 5. 이 파일을 고칠 때

- **검사를 늘리면 §2의 주입 시험 칸을 함께 채운다.** 비우면 §3.10-1 위반이다
- **필드를 늘리면 그것을 읽는 검사를 함께 세운다.** 아무도 안 읽는 필드는 뒤에 아무거나 담긴다
- 스키마를 바꾸면 기존 항목이 깨진다. 원장은 수정 불가이므로 **필드 추가는 선택 필드로만 하고,
  기존 항목에 소급해 채우지 않는다**
