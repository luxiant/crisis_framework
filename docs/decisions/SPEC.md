# SPEC.md — 원장의 스키마와 검사 목록

이 파일은 `docs/decisions/` 원장의 **스키마와 검사 목록의 정본**이다. 판단을 요구하는 조항은
세션 지시 §3.7(R-6 ~ R-10)과 §5.6이 들고, 이 파일은 그것을 기계가 읽는 형태로 내린다.

**검사 목록이 먼저이고 스키마는 거기서 유도됐다.** 반대 순서로 가면 조항은 있는데 검사가 없는
자리가 생긴다. 그래서 이 문서는 §2에 검사를 먼저 놓고 §3에 스키마를 놓는다. 스키마의 모든
필드는 §2의 어느 검사가 읽는 것이며, 어느 검사도 읽지 않는 필드는 두지 않는다.

---

## 0. 정체와 비목적

### 0.1 원장이 드는 것

낙착과 그 **사유와 실측 근거**다. 규율의 집행 문면은 세션 지시와 `CLAUDE.md` 가 들고 원장은
그것이 어떤 실패를 잡으려 섰는지를 든다. 둘이 드는 것이 다르므로 전사가 아니다.

### 0.2 원장이 들지 않는 것

- **코드의 위치.** 파일 경로와 줄번호를 항목에 넣지 않는다. 코드 쪽 링크는 Lean 주석의
  `-- DD:<id>` 가 들고 `grep` 으로 복원한다. 경로를 넣으면 리팩터링마다 원장이 낡는다
- **값.** 공리 기준선과 툴체인 핀과 오염 어간은 `docs/baseline.md` 가 든다
- **아크와 페이즈의 값.** `arcs.json` 이 든다. 원장은 그것을 `origin` 으로 지목만 한다
- **살아 있음.** 저장하지 않고 유도한다. 자기를 가리키는 폐기 레코드가 없으면 살아 있다

### 0.3 수정하지 않는다

항목이 일단 쓰이면 어떤 필드도 고치지 않는다. 폐기는 **폐기 레코드를 새로 쓰는 것**이며 원
항목을 건드리지 않는다. 상태 필드를 고치는 방식은 추가로 위장한 수정이므로 쓰지 않는다(R-9).

**재분류도 수정이 아니다.** 구멍이 해소되면 결정 항목을 새로 쓰고 그 구멍을 가리키는 폐기
레코드를 쓴다. 구멍 항목은 제자리에 그대로 남는다. 그래서 항목이 파일 사이를 옮겨 다닐 일이
없다.

## 1. 파일 구성

| 파일 | 담는 것 |
|---|---|
| `decisions.json` | 결정. 규율 조항과 확정 결정과 독해 산출 |
| `deferred.json` | 정의 구멍과 탐구 미결 |
| `rejected.json` | 기각한 정의 후보 |
| `glossary.json` | 용어집 개념과 관계 |
| `retirements.json` | 폐기 레코드 |
| `arcs.json` | 아크와 페이즈와 패치 (리포 루트) |

**ID 공간은 전 파일에 걸쳐 하나다.** `CF-<n>` 단조 증가이며 재사용하지 않는다. 종류는 파일이
들고 접두사에 박지 않는다. 참조 구현에서 종류를 접두사에 박은 결과 같은 계열이 두 파일에 걸치게
됐고, 그것을 잡으려고 검사를 하나 더 세워야 했다.

**`invariants` 파일을 따로 두지 않는다.** 불변식은 종류가 아니라 **티어**이며 `decisions.json`
안에서 `tier` 가 든다. 참조 구현은 둘을 다 두어 같은 축이 두 자리에 섰다.

## 2. 검사 목록

각 검사는 **그것이 잡아야 할 위반을 주입했을 때 실패하는지**를 확인한다(§3.10-1 음성 대조).
통과만 보고 검사가 동작한다고 판단하지 않는다. 주입 시험의 대상을 검사마다 함께 적는다.

### 2.1 실패시키는 검사 (열다섯)

| | 검사 | 잡는 실패 | 주입 시험 |
|---|---|---|---|
| **1** | `id` 가 `CF-<n>` 형식이고 전 파일에서 유일한가 | 마커 충돌 | 같은 id를 두 파일에 넣는다 |
| **2** | `origin.arc` 가 `arcs.json` 의 아크 이름에 실재하는가 | **아크명 누락** | 없는 아크명을 적는다 |
| **3** | `origin.phase` 가 그 아크의 `phases` 에 있는가 | 페이즈가 선언 없이 생기는 것 | 선언되지 않은 페이즈를 적는다 |
| **3-a** | `origin.phase` 가 `origin.arc + "-" + <n>` 형태인가 | 아크와 페이즈가 어긋나는 것 | 다른 아크의 페이즈명을 적는다 |
| **4** | 3이 실패할 때 `arcs.json` 의 `patches` 가 그 페이즈에 권한을 주는가 | 계획이 조용히 달라지는 것 | 패치 없이 페이즈를 늘린다 |
| **5** | `status: closed` 인 아크에 새 항목이 드는가 | 아크 종료의 무의미화 | 닫힌 아크로 항목을 쓴다 |
| **6** | `tier` 가 `invariant`·`policy`·`finding` 중 하나인가 | 티어 어휘 드리프트 | `tactical` 을 적는다 |
| **7** | `tier: invariant` 인 항목의 `check` 가 `verify.sh` 의 선언된 단계에 실재하는가 | **티어의 거짓 주장** | 없는 단계명을 적는다 |
| **8** | 폐기 레코드의 `target` 이 실재하고 한 대상에 폐기가 둘 이상이 아닌가 | 폐기 정합 | 같은 대상을 두 번 폐기한다 |
| **9** | 폐기 레코드에 `original` 과 `reason` 이 비어 있지 않은가 | 폐기 사유의 소실 | `reason` 을 비운다 |
| **10** | **폐기된 id를 살아 있는 것처럼 참조하는 자리가 있는가** | 유령 | 폐기된 id를 `related` 에 넣는다 |
| **11** | `deferred` 항목에 `reopen_when` 이 있고 `kind` 가 넷 중 하나인가 | 트리거 없는 등재 | `kind` 를 비운다 |
| **12** | `reopen_when.ref` 가 `kind` 별 대상에서 해소되는가 | 트리거가 가리키는 곳이 없는 것 | 없는 추출 번호를 적는다 |
| **13** | Lean의 `DD:` 표지가 실재하고 폐기되지 않은 id를 가리키는가 | 끊긴 표지 | 없는 id를 주석에 적는다 |
| **14** | `DD:` 항목의 `layer` 가 그 파일이 사는 층과 같은가 | 결정이 엉뚱한 층에서 인용되는 것 | 회계층 파일에서 정의층 항목을 지목한다 |
| **15** | `names` 에 적힌 규율 ID가 다른 항목의 `names` 에 실재하는가 | 규율 지목의 유령 | 폐기된 규율 ID를 적는다 |

**검사 10의 범위는 원장 밖으로 나간다.** 폐기된 id를 참조하는 자리가 셋이다. 원장 안의
`related` 와 `reopen_when.ref`, Lean 파일의 `DD:` 표지, `docs/` 산문의 인용이다. 셋을 다 훑되
**폐기 레코드 자신의 `target` 과 `original` 은 제외한다.** 그것은 폐기를 기록하는 자리이지 산
참조가 아니다.

**검사 15는 자기 폐포로 성립한다.** 규율의 정본인 세션 지시는 리포 밖에 있어 대조할 수 없다.
그런데 규율 조항이 원장 항목으로 들어오므로, `names` 에 적힌 ID가 다른 항목의 `names` 에
실재하는지를 물으면 리포 안에서 닫힌다. **규율을 먼저 역유입해야 이 검사가 의미를 갖는다**(J-23).

### 2.2 보고만 하는 검사 (넷)

실패시키지 않고 계수와 목록을 낸다.

| | 보고 | 왜 실패가 아닌가 |
|---|---|---|
| **16** | `reopen_when` 이 충족된 이연 항목 | **발화 탐지.** 트리거를 써 놓고 아무도 안 보면 구멍이 영영 잔다 |
| **17** | `reopen_when: null` 인 항의 계수 | R-7이 등재는 허용하되 계수로 보고하게 했다 |
| **18** | 아크별 `blocking` 구멍의 처분 내역 | 아크를 닫을 때 셋 중 하나여야 하나, 내역 자체는 보고 대상 |
| **19** | `CF-<n>` 번호의 결번 | 결번이 곧 결함은 아니나 삭제의 흔적일 수 있다 |

**검사 16이 없으면 `blocking` 트리거가 무의미하다.** 발화 신호가 리포에 흔적을 남긴다는 것이
R-7의 전제인데, 그 흔적을 읽는 쪽이 없으면 흔적만 남고 아무 일도 일어나지 않는다.

### 2.3 아크 종료 시 검사

아크를 닫을 때만 도는 검사다. `status` 를 `closed` 로 바꾸는 커밋에서 실행한다.

| | 검사 |
|---|---|
| **20** | 그 아크에 걸린 구멍마다 해소됐거나 이관됐는가 |
| **21** | 그 아크에 걸린 `blocking` 구멍마다 발화했거나, 진술이 쓰였는데 막히지 않아 해소됐거나, 진술을 쓰지 않아 이월됐는가 |

21이 없으면 **발화시킬 진술을 아무도 쓰지 않은 구멍이 영영 자고, 겉으로는 해소된 것과 구별되지
않는다.**

## 3. 스키마

필드마다 그것을 읽는 검사 번호를 단다. **어느 검사도 읽지 않는 필드는 두지 않는다.**

### 3.1 공통 필드

모든 레지스터의 항목이 갖는다.

| 필드 | 형 | 검사 | 뜻 |
|---|---|---|---|
| `id` | `"CF-<n>"` | 1 | 불변 앵커 |
| `origin` | 객체 | 2·3·3-a·4·5 | 어느 아크의 어느 페이즈에서 나왔는가 |
| `statement` | 문자열 | | 무엇이 정해졌는가. 한 문장 |
| `basis` | 문자열 | | **사유와 실측 근거.** 어떤 실패를 잡으려 섰는가 |
| `related` | `["CF-<n>"]` | 10 | 다른 항목 참조 |

`origin` 의 내부는 이렇다.

```json
"origin": {
  "arc":   "claim",
  "phase": "claim-3",
  "kind":  "decision_session",
  "date":  "2026-09-19"
}
```

**`arc` 와 `phase` 의 중복은 의도된 것이다.** 값 하나만 옮겨 적어도 아크가 따라오고, 둘이
어긋나면 검사 3-a가 잡는다. 참조 구현이 페이즈를 그리스 문자 하나로 두어 산문에 무심코
흩뿌려졌고 그때마다 아크명이 빠졌다. 실측하면 2088건이었다.

`kind` 는 `decision_session` · `reading` · `handoff_return` 셋이다.

`basis` 는 한 줄로 끝내지 않는다. 참조 구현은 한 줄이었으나 이 프로젝트는 밀도가 더 높아야
한다. C-9만 해도 실측 근거와 구조적 근거와 비용 인정이 붙는다.

### 3.2 `decisions.json`

| 필드 | 형 | 검사 | 뜻 |
|---|---|---|---|
| `tier` | `invariant`\|`policy`\|`finding` | 6·7 | R-10 |
| `layer` | 아래 여섯 | 14 | 어느 형식층의 결정인가 |
| `names` | `["C-10", ...]` | 15 | 이 항목이 드는 규율 조항의 이름 |
| `check` | 문자열 | 7 | `verify.sh` 의 단계 id. `tier: invariant` 면 필수 |

`layer` 의 값은 `glossary` · `definition` · `accounting` · `dynamics` · `observation` · `meta`
여섯이다. 앞의 다섯이 형식층이고 `meta` 는 규율과 작업 흐름처럼 층에 살지 않는 것이다.

**검사 14의 대응표.**

| `layer` | 디렉터리 |
|---|---|
| `glossary` | `CrisisFramework/Glossary/` |
| `definition` | `CrisisFramework/Definition/` |
| `accounting` | `CrisisFramework/Accounting/` |
| `dynamics` | `CrisisFramework/Dynamics/` |
| `observation` | `CrisisFramework/Observation/` |
| `meta` | (어느 Lean 파일에서도 `DD:` 로 지목하지 않는다) |

`names` 는 선택이다. 규율 조항이 아닌 결정은 이름을 갖지 않는다.

### 3.3 `deferred.json`

| 필드 | 형 | 검사 | 뜻 |
|---|---|---|---|
| `layer` | 위 여섯 | 14 | |
| `reopen_when` | 객체 \| `null` | 11·12·16·17 | 재개 트리거 |

```json
"reopen_when": { "kind": "blocking", "ref": "claim", "what": "발동조건 문법이 V-2의 네 관계로 표현되지 않는 자리" }
```

**`kind` 는 넷이다.**

| `kind` | `ref` 가 가리키는 것 | 검사 12가 해소하는 곳 |
|---|---|---|
| `artifact` | 리포 경로 | 파일시스템 |
| `extraction` | `E-nn` | `reading-queue-v0.md` |
| `arc_phase` | 아크 이름 | `arcs.json` (`status: reserved` 포함) |
| `blocking` | 그 진술을 쓸 아크 이름 | `arcs.json` |

`blocking` 은 "이것 없이 진행되는 동안은 자고, 이것을 요구하는 진술이 실제로 막히면 깬다"를
뜻한다. 발화 신호는 그 자리의 `sorry` 이거나 빌드 실패이거나 막힘 보고이며 셋 다 리포에 흔적을
남긴다. **판정자가 사람이 아니라 형식화라는 점에서 P-1과 같은 축이다.**

`arc_phase` 의 `ref` 가 아직 열리지 않은 아크를 가리킬 수 있다. `arcs.json` 에 `status:
reserved` 로 이름만 예약해 두면 된다. 범위 밖으로 밀려 있는 구멍이 거기에 걸리고, 예약 아크가
열리는 순간 한꺼번에 발화한다.

`reopen_when: null` 은 허용하되 검사 17이 계수로 보고한다. **재개 조건을 못 쓴다는 사실 자체가
P-1이 찾는 종류의 관측일 수 있다.**

### 3.4 `rejected.json`

| 필드 | 형 | 뜻 |
|---|---|---|
| `candidate` | 문자열 | 기각된 정의 후보의 문면 |
| `reason` | 문자열 | 기각 사유 |
| `for` | 문자열 | 무엇의 대체 후보였는가 |

D-2 3항이 docstring에 드는 것과 같은 대상이다. **docstring이 요지를 들고 원장이 사유를 든다**
(R-8).

### 3.5 `glossary.json`

| 필드 | 형 | 뜻 |
|---|---|---|
| `term` | 문자열 | 한국어 개념명 |
| `ident` | 문자열 | Lean 식별자 |
| `relations` | 배열 | V-2의 네 관계 |

`relations` 의 각 항은 `{"kind": ..., "to": ...}` 이고 `kind` 는 `refine` · `exclusive` ·
`partition` · `measure` 넷이다. **다섯째를 임의로 늘리지 않는다.** 표현되지 않는 관계는
구멍으로 올린다(G-5).

### 3.6 `retirements.json`

| 필드 | 형 | 검사 | 뜻 |
|---|---|---|---|
| `target` | `"CF-<n>"` | 8·10 | 폐기되는 항목 |
| `original` | 문자열 | 9 | 그 항목의 원문 |
| `reason` | 문자열 | 9 | **어떤 실패를 잡으려 섰고 왜 그 틀이 깨졌는가** |
| `replaced_by` | `"CF-<n>"` \| `null` | 8 | 대체 |

폐기 레코드 자신도 `id` 와 `origin` 을 갖는다. 언제 어느 페이즈에서 폐기했는지가 남아야 하기
때문이다.

**`reason` 이 비면 안 되는 근거는 실측이다.** 참조 구현은 폐기 사유를 패치 문서에 두어 원장만
보고는 그 조항이 어떤 실패를 잡으려 섰는지 알 수 없었다. 그리고 원 초안이 소실된 계열은 문면을
패치 헤더에서 재구성해야 했다.

### 3.7 `arcs.json`

```json
{
  "arcs": [
    {
      "name": "claim",
      "discriminator": "청구권 발동조건을 어떤 문법으로 쓰는가",
      "ph": "PH-2",
      "phases": ["claim-1", "claim-2", "claim-3"],
      "status": "open",
      "opened": "2026-09-19",
      "closed": null,
      "holes": ["CF-120", "CF-121"],
      "cq": ["CQ-fin-1"]
    }
  ],
  "patches": [
    {
      "arc": "claim",
      "phase": "claim-4",
      "op": "add",
      "why": "...",
      "origin": { "arc": "claim", "phase": "claim-3", "kind": "decision_session", "date": "..." }
    }
  ]
}
```

| 필드 | 검사 | 뜻 |
|---|---|---|
| `name` | 2 | 아크 이름. `origin.arc` 가 이것을 가리킨다 |
| `discriminator` | | **판별선 하나.** 둘 이상이면 아크가 아니다 |
| `phases` | 3·3-a | **개막 시 정한 전량** |
| `status` | 5 | `open` · `closed` · `reserved` |
| `holes` | 20·21 | 이 아크에 걸린 구멍 |
| `cq` | | 내리려는 `CQ-fin` 항 |

`patches` 의 `op` 는 `add` · `move` · `split` · `drop` 이다. **추가만 하며 앞 레코드를 고치지
않는다.** 이 배열이 검사 4의 권한 원천이므로, 선언되지 않은 페이즈로 항목이 들어오면 여기에
레코드가 있어야 통과한다. **관행이던 것이 기계 검사가 된다.**

`discriminator` 를 읽는 검사가 없다. 판별선이 하나인지는 기계가 셀 수 없으므로 W-6의 리뷰
항목이다. 필드로 두는 것은 아크를 열 때 그것을 쓰게 강제하기 위해서다.

## 4. 검증기

`scripts/check_wiki.py` 가 §2의 검사를 돈다. `scripts/verify.sh` 가 그것을 호출하고 CI가
`verify.sh` 를 돈다.

**Claude Code는 이 검증기와 CI 워크플로를 고쳐 통과시키지 않는다.** 검사가 실패하면 그 실패가
산출물이다.

**현행 뷰를 매 커밋에 생성한다.** 살아 있음을 저장하지 않고 유도하므로(§0.2) 항목 하나만 봐서는
그것이 살아 있는지 알 수 없다. 폐기 색인을 함께 읽어야 하는 비용을 생성물이 흡수한다. 생성물은
원장이 아니므로 고쳐도 되고 지워도 되며, 매번 다시 만들어진다.

## 5. 이 파일을 고칠 때

- **검사를 늘리면 §2의 주입 시험 칸을 함께 채운다.** 비우면 §3.10-1 위반이다
- **필드를 늘리면 그것을 읽는 검사를 함께 세운다.** 아무도 안 읽는 필드는 뒤에 아무거나 담긴다
- 스키마를 바꾸면 기존 항목이 깨진다. 원장은 수정 불가이므로 **필드 추가는 선택 필드로만 하고,
  기존 항목에 소급해 채우지 않는다**
